# Open OCR CLI Launch Playbook

The product position is deliberately narrow: **provider-neutral, production-safe
multimodal OCR from the terminal**. Lead with a useful document result, not a
list of model logos. Provider choice, cost controls, and gateways are the proof
that the workflow is portable.

## Launch assets

Prepare these from the tagged release so every claim is reproducible:

- a 45–60 second terminal recording: install, extract an invoice, show JSON,
  switch the same command from Gemini to Kimi through OpenRouter;
- one public benchmark table generated by the evaluation matrix, including
  quality, p50 latency, and billed or estimated cost with the exact suite/date;
- three copy-paste recipes: local batch OCR, GitHub Action invoice extraction,
  and Cloudflare AI Gateway routing;
- one architecture image based on the provider-adapter diagram in the README;
- an honest limitations card covering model-dependent schemas/tools, provider
  preview status, and the fact that live extraction sends documents upstream.

## Thirty-day sequence

### Week 1 — credible release

- Publish v2 to npm, GitHub Releases, GHCR, Homebrew formula, and the GitHub
  Marketplace Action from the same tagged commit.
- Pin a concise demo issue or Discussion with the terminal recording and exact
  reproduction command.
- Ask five document-automation users to complete install → doctor → first
  extraction without help. Turn every failure into an onboarding fix.

### Week 2 — useful examples

- Publish focused recipes for invoices, receipts, PDFs in CI, custom JSON
  Schemas, OpenRouter model switching, and Cloudflare observability.
- Share the benchmark methodology and raw configuration, not only the winning
  number. Invite providers and users to contribute reproducible cases.
- Label small documentation, fixture, and provider-profile tasks as
  `good first issue`.

### Week 3 — distribution

- Submit the Action to GitHub Marketplace and share the release in communities
  where CLI automation and document processing are already discussed. Adapt
  the example to each community instead of reposting generic launch copy.
- Create a Homebrew tap if formula installs are meaningfully used; until then,
  keep the signed release formula as the low-maintenance path.
- Reach out to Kimi, Meta, OpenRouter, and Cloudflare developer-relations teams
  with the provider-specific demo and reproducible eval result.

### Week 4 — retention

- Publish the first monthly provider matrix and explain regressions or routing
  changes.
- Prioritize the top repeated activation blocker and top extraction-quality
  failure over adding another provider logo.
- Turn two real workflows into short case studies with sample inputs that are
  safe to redistribute.

## Metrics that matter

Track a small funnel weekly:

| Stage | Metric | Initial signal |
| --- | --- | --- |
| Discovery | npm page views, GitHub unique visitors, demo views | Which example attracts qualified users? |
| Activation | successful `doctor`, first extraction, Action runs | Can a new user get value in ten minutes? |
| Value | documents completed, resumed batches, structured outputs | Is this used beyond a toy command? |
| Retention | repeat weekly runs and returning repositories | Does it become part of a workflow? |
| Trust | issue response time, eval regressions, release provenance | Is adoption safe for automation? |

Do not add telemetry to document processing by default. Measure public package,
repository, release, and opt-in community signals; ask users for anonymized
workflow counts when deeper product learning is needed.

## Launch copy

> Open OCR CLI extracts text and structured data from images, PDFs, and URLs
> with Gemini, Kimi K2.6, Muse Spark 1.1, OpenRouter, or your own compatible
> endpoint. It is resumable, pipeline-safe, schema-validated, cost-aware, and
> can route through Cloudflare AI Gateway.

The call to action should be one command:

```bash
npx open-ocr-cli extract invoice.pdf --dry-run
```

Then show the credentialed command for the provider used in the demo.
